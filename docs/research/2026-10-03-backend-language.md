# バックエンド言語の選定（Go / Rust / TypeScript、最初の対象は Go のリポジトリ）

確認日: 2026-10-03。凡例: [直] = gh api・raw ファイル・npm/crates.io API・手元実行。[要約] = WebFetch の要約経由。[推] = 推論。既存の 3 記録が確定させた事項（LSP over stdio、inlay hint は長文に不向き、Harper と typos-lsp の先例）は再調査していない。

## 答え

**Go を推奨する。** 根拠は 2 点。

1. 要件の部品が Go 標準か公式 `golang.org/x/tools` にあり、現役で保守されている。`go/packages`（`Config.Overlay`）、`go/ast`、`go/types`、`cover.ParseProfiles`、`cmd/test2json` 相当の型。Rust と TS には cover profile と test2json を読む保守されたライブラリが無く、型情報（`go/types` 相当）も無い。
2. Go のツールチェーン周辺の LSP サーバ（sqls、efm-langserver、golangci-lint-langserver、buf、terraform-ls）は Go 製が標準的。単一バイナリの配布も最も素直。

Rust は起動と大きさで僅かに勝る（1.2 ms 対 1.7 ms、0.47 MB 対 2.5 MB）が、LSP の応答時間には効かない差。TS は Neovim 利用者に Node を要求するか、63〜111 MB の単一バイナリになる。

ユーザー体感に効くのはバックエンドの起動ではなく、`go test -c -race` のビルドと実行。ここは言語に依らない。

## 根拠

| 部品 | 状態 | 出典 |
|---|---|---|
| golang/tools | 8,006★、push 2026-10-02 | https://github.com/golang/tools [直] |
| `cover.ParseProfiles` | 「Package cover provides support for parsing coverage profiles generated by "go test -coverprofile=cover.out"」 | https://raw.githubusercontent.com/golang/tools/master/cover/profile.go [直] |
| `go/packages` の `Config.Overlay` | 「Load uses the alternative file contents provided by the overlay mapping instead of reading from the file system」 | https://pkg.go.dev/golang.org/x/tools/go/packages [要約] |
| 同上の注意 | LoadMode の組み合わせに open bug（Go #56633, #56677, #58726, #63517）。`NeedTypes` と `NeedDeps` の併用は高コスト | 同上 [要約] |
| gopls の呼び出し階層 | 「Dynamic calls are not included」。動的呼び出しは取れない | https://raw.githubusercontent.com/golang/tools/master/gopls/doc/features/navigation.md [要約] |

- `go build -overlay` は `go test` 経由では効かないが、`go test -c -overlay` でテストバイナリを作り、それを直接実行すれば効く。2026-10-03 に手元で確認済み（`testdata/go/copyrace`、race 20/20 回検出、ビルド 0.8 秒、キャッシュ後 0.08 秒）[直]。

### 先例

Go 製: gopls、sqls、efm-langserver、golangci-lint-langserver、buf、terraform-ls。Rust 製: harper-ls、typos-lsp（どちらも自然言語やテキストが対象で、コンパイラの情報を要しない）。「最初の対象が Go で、`go/types` を要する Rust 製 LSP」の先例は見つからなかった。

## 注意点

- 推奨の中心は部品の有無で、速さではない。
- 後から Rust / TS / Python を対象にするとき、tree-sitter の Go バインディング（go-tree-sitter 298★、2025-11 で停止気味）は Rust と TS より弱く、CGO でクロスコンパイルが面倒になる [直]。後続言語は tree-sitter ではなく、各言語のツールチェーン（`cargo test -- --format json`、vitest の reporter、pytest の JSON）と、エディタの LSP から得る関数の範囲で済ませる設計にすれば、この弱点は避けられる [推]。
- `go/callgraph` は SSA 前提で重い。1 関数の周りの呼び出し元は、`go/packages` + `go/ast` で呼び出し式を拾う近似になる見込み [推]。
